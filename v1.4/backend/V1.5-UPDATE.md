# Moshaver v1.5 — Student Management + Learning Loop

## Goal and implementation plan

This release improves the existing Node.js + SQLite + vanilla PWA architecture without replacing it.

1. Preserve the existing authentication, CSRF, cookie, SSE and SQLite model.
2. Make student account lifecycle management easier and safer.
3. Add full exam/practice attempt history with answer-level review.
4. Convert wrong/blank answers into an explicit relearning workflow.
5. Let students and advisors add notes, hints and book/chapter/lesson context.
6. Schedule the next review from a simple mastery rating instead of adding opaque ML infrastructure.
7. Enrich the admin live view with actionable current-state information.
8. Keep all schema changes additive and test them against a fresh SQLite database.
9. Keep the frontend lightweight for low-end Android devices.

## Database migration

`src/migrations/003_learning_journal.js` is additive.

It adds optional learning metadata to `quiz_questions`:

- `book`
- `chapter`
- `lesson`
- `topic`
- `hint`

It creates `learning_items` for the per-student learning journal. A learning item may reference the exact submitted answer that created it and stores subject/book/chapter/lesson/topic, note, hint, due date, mastery, interval and review count.

No existing table or production row is deleted.

## Learning behavior

When a student submits a wrong or blank answer, the backend creates one learning item for that answer if one does not already exist. The first review is due the next day.

After a review the student selects mastery from 1 to 5. The next interval is deliberately simple and explainable:

- 1 → 1 day
- 2 → at least 2 days
- 3 → at least 3 days, then grows gradually
- 4 → at least 7 days, then grows faster
- 5 → at least 14 days, with a maximum interval of 90 days

Repeated high mastery may archive the item. The system can be tuned later without changing the data model.

## New/additive API operations

Student learning:

- `GET /api/v1/learning/summary`
- `GET /api/v1/learning/items`
- `POST /api/v1/learning/items`
- `PATCH /api/v1/learning/items/:id`
- `POST /api/v1/learning/items/:id/review`
- `DELETE /api/v1/learning/items/:id`

Student attempt history:

- `GET /api/v1/quizzes/history`
- `GET /api/v1/quizzes/history/:attemptId`

Admin learning + attempt review:

- `GET /api/v1/admin/students/:studentId/learning`
- `POST /api/v1/admin/students/:studentId/learning`
- `PATCH /api/v1/admin/students/:studentId/learning/:itemId`
- `DELETE /api/v1/admin/students/:studentId/learning/:itemId`
- `GET /api/v1/admin/students/:studentId/attempts`
- `GET /api/v1/admin/students/:studentId/attempts/:attemptId`

Question CRUD improvement:

- `PATCH /api/v1/admin/questions/:questionId`

Student lifecycle:

- `DELETE /api/v1/admin/students/:studentId` performs safe deactivation, not destructive deletion.
- `POST /api/v1/admin/students/:studentId/activate` reactivates the account.

## Realtime behavior

The existing SSE transport is preserved.

New realtime/activity events include:

- `learning.created`
- `learning.reviewed`
- `learning.updated`
- `attempt.reviewed`
- `screen.viewed`

When an advisor creates a learning item, the student receives an in-app notification plus `learning.updated` over SSE. Admin live activity can also show which major screen the student most recently opened.

## Security

- Student attempt detail is scoped to the authenticated student's own attempts.
- Learning CRUD is scoped to the authenticated student or an admin-selected student endpoint.
- Source answer IDs are ownership-checked before a learning item can reference them.
- Deactivation revokes active sessions.
- Existing cookie, CSRF, CORS, rate-limit and password hashing behavior remains in place.
- Student history is preserved when an account is deactivated.

## Validation

Expected commands for this release:

```bash
npm run check
npm run test:learning-api
npm run smoke
```

`test:learning-api` covers account creation, login, question create/update, quiz submission, attempt history/detail, automatic learning-item creation, notes/hints, adaptive review scheduling, admin learning SSE and student deactivate/reactivate.

## Deliberately deferred

- No React/Next/Nest/ORM/database migration.
- No destructive permanent student deletion UI.
- No opaque ML model. The current analysis uses attempt results, mistake reasons, subject aggregates, mastery and due-review counts so advisors can understand why a recommendation exists.
- OS-level push notifications and scheduled background notification jobs are not introduced in this release; due learning items are surfaced inside the student dashboard, and advisor-created items arrive immediately through existing notification + SSE infrastructure.
