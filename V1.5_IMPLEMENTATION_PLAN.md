# Moshaver v1.5 Implementation Plan

## Goal

Ship **v1.5 — Advisor Intelligence** on top of the current dependency-light Node.js + SQLite backend and framework-free Student/Admin applications, while keeping the existing v1.4 auth, session, planner, exam, chat, SSE, notification, offline and PWA behavior stable.

The release should help the advisor answer four questions quickly:

1. What needs attention today?
2. Is the student ready for the next exam, and why?
3. Where is the student repeatedly weak or falling behind?
4. What should change in tomorrow's plan?

## Guardrails

- Keep the existing v1.x stack for v1.5. Do **not** migrate to React/NestJS/PostgreSQL/Redis here; that remains v2 work.
- Intelligence must be deterministic and explainable. No LLM is required for core scoring.
- The system may **propose** plan changes, but the advisor must approve/edit/reject them before they affect the student.
- Preserve server-authoritative scoring, session security, CSRF, timed-exam enforcement, same-origin proxying, and additive SQLite migrations.
- Preserve low-end Android performance and offline/PWA behavior.
- Student-facing dates should remain Shamsi-first; Admin date entry/display should become consistent as part of this release.

## Existing data to reuse

v1.4 already records enough signals to build the first intelligence layer without a new datastore:

- plans, tasks and task completions
- daily reports and actual study/test counts
- study sessions and activity events
- quiz attempts, quiz answers and mistake reasons
- exam syllabus progress and accuracy
- review items / due reviews
- task issues and recovery requests
- exam attempt requests
- advisor comments, chat unread state and notifications

## Phase 0 — Runtime and release safety

### 0.1 Separate development and production profiles

Make local development, local UI → production API, and full production modes explicit and difficult to confuse.

Acceptance goals:

- one command for full local development
- one command for local Admin against production API
- one command for local Student against production API when needed
- production compose/example never uses insecure cookie settings or default credentials silently
- proxy startup prints target, mode and health result
- README documents the three modes clearly

### 0.2 Release regression baseline

Before intelligence work, extend validation around auth, planner, imports, exams, SSE/chat, notifications, offline queue and proxy behavior so v1.5 cannot regress v1.4.

## Phase 1 — Intelligence metrics foundation

Add a small backend intelligence module/service layer that computes normalized metrics from existing tables. Keep storage additive and minimal.

Core metrics:

- plan adherence percentage
- planned vs actual study minutes
- planned vs actual tests
- completion streak / missed-day streak
- subject accuracy trend
- repeated mistake count by subject/topic/reason
- due/overdue review debt
- syllabus coverage and recent accuracy
- workload minutes/tasks per day
- late completion / reschedule / recovery-request frequency

Expose a versioned Advisor intelligence response so the Admin UI does not duplicate scoring logic.

## Phase 2 — Explainable Advisor Intelligence

### 2.1 Exam readiness

Replace the current simple readiness percentage with an explainable score composed from:

- syllabus coverage
- recent quiz accuracy
- review debt
- plan adherence
- recent study volume
- repeated mistakes
- recency of evidence

Every score must return component values and human-readable reasons, for example: `72% — coverage is good, but 4 overdue reviews and weak recent accuracy in علوم و فنون reduce readiness.`

### 2.2 Weakness and mistake trends

Group wrong answers and mistake reasons by subject/topic and time window. Show whether each weakness is improving, stable or worsening.

### 2.3 Review debt and study consistency

Calculate due/overdue review pressure, completion consistency, streaks and recovery behavior. Avoid simplistic red/green status; provide severity plus evidence.

### 2.4 Workload/fatigue signals

Detect risky workload using explainable heuristics such as excessive planned minutes, too many long blocks, repeated partial/missed tasks, late-day overload and recent recovery requests. This is a planning signal, not a medical diagnosis.

## Phase 3 — Advisor actions

### 3.1 Tomorrow-plan recommendations

Generate deterministic recommendations such as:

- reduce or split an overloaded block
- move overdue review earlier
- add targeted practice for a weak topic
- reduce new material before an exam
- increase practice when coverage is high but accuracy is low

Recommendations must have `proposed`, `approved`, `rejected`, and `applied` states. Applying a recommendation should create/update plan data through the existing planner rules and audit the advisor action.

### 3.2 Weekly Advisor summary

Provide a compact weekly summary containing:

- study adherence and total actual minutes
- tests completed and accuracy trend
- strongest improvement
- top weaknesses
- review debt
- workload warnings
- next-exam readiness
- recommended priorities for next week

### 3.3 Advisor dashboard UX

Keep the existing exception/action-oriented design. Put urgent student actions first, then intelligence cards, then detail views. The advisor should be able to go from a warning to the relevant plan/exam/mistake/review in one action.

## Phase 4 — Student experience

The Student app should remain focused on **"الان باید چه کاری انجام بدهم؟"**.

Only advisor-approved changes should alter the student's plan. Student-facing additions should stay lightweight:

- clearer current/next priority
- due-review indicator
- next-exam readiness explanation in simple language
- approved plan adjustment notice
- consistent Shamsi date presentation

Do not turn the Student home into an analytics dashboard.

## Phase 5 — Data safety, testing and release gates

### Data safety

- additive SQLite migrations only
- backup before schema-changing deployment
- import preview must remain non-destructive
- intelligence calculations must tolerate incomplete historical data

### Test coverage

Add automated coverage for:

- metric calculations and edge cases
- exam readiness component math
- weakness trend windows
- review-debt calculations
- workload/fatigue heuristics
- recommendation approval/rejection/application
- weekly summaries
- existing v1.4 auth/exam/import/chat/SSE contracts

### Release gates

v1.5 is ready only when:

- `./scripts/validate-pack.sh` passes
- backend smoke tests pass with a clean DB and an upgraded v1.4 DB
- local full-stack mode works
- local Admin → production proxy mode works
- Student PWA works on a low-end Android viewport/device profile
- no major regression exists in offline, SSE reconnect, chat autoscroll, timed exams or session persistence

## Recommended issue order

1. Runtime profiles and proxy diagnostics
2. v1.5 regression baseline
3. Intelligence metrics foundation/API
4. Explainable exam readiness
5. Weakness/mistake trends
6. Review debt and study consistency
7. Workload/fatigue signals
8. Tomorrow-plan recommendations + Advisor approval
9. Weekly Advisor summary + Admin intelligence UX
10. Student priority/readiness UX + complete Shamsi consistency
11. Backup/restore, import diagnostics and final v1.5 release gate

## Out of scope for v1.5

- multi-advisor/multi-tenant SaaS architecture
- subscriptions/billing
- monorepo/framework migration
- PostgreSQL/Redis/BullMQ/S3 migration
- microservices
- autonomous AI changing plans without Advisor approval
